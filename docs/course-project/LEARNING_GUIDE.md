# 从代码到答辩：课程版学习路线

本文件帮助你解释自己实际实现的系统。先运行 [本地演示](DEPLOYMENT.md)，再沿下面的顺序阅读；不要一开始同时读完整仓库。

## 第一步：讲清业务和边界

阅读 `REQUIREMENTS.md` 和 `CONTRACT.md`，画出“赞助 100 DUSD → 托管 → 审核 → 赢家领取”的资金流，再画“赛事取消 → 原赞助者退款”的分支。

能够回答：

- 谁拥有资产？谁可以改比赛结果？谁可以触发付款？
- 为什么赞助方先出资，而不是获胜后再承诺付款？
- 为什么当前两人比赛报名免费、没有观众下注？
- 区块链能保证资金规则、历史不可随意修改；它如何依赖审核员判断链下事实？

练习：用三个浏览器钱包身份分别扮演主办方、参赛者、审核员，尝试执行一个越权操作，记录拒绝发生在哪一层。

## 第二步：理解合约状态机与资产安全

依次读：

1. `contracts/src/CourseTypes.sol`：状态与数据结构。
2. `TournamentManager.sol`：对外操作及角色、时间、状态校验。
3. `TournamentRegistry.sol`：比赛状态与报名快照。
4. `PrizeEscrow.sol`：每场出资、总负债、领奖与退款。
5. `ResultReview.sol`：结果、异议、审核证据。
6. `contracts/test/`：用测试确认规则，尤其失败场景。

画出以下恒等关系：

`某赛事未支付金额 = totalFunded - totalPaid`

`合约总负债 = 所有赛事尚可领取的奖金或退款之和`

解释以下设计：

- `onlyManager` 保护内部合约，所有钱包经过同一业务入口。
- ERC20 授权给真正执行 `transferFrom` 的 `PrizeEscrow`。
- 状态先改变、资金后转出，重入锁再增加一层保护。
- 领取模式不遍历全部赞助者；单次提取的 Gas 不随赞助人数线性增长。
- 超时退款允许任何人触发取消，但每个人只能领取属于自己的款项。

练习：临时删除一个状态校验，观察哪条测试先失败；随后恢复代码。把“旧换边下注为什么会多领”和“新赞助账本为什么不会”写成自己的推导。

## 第三步：理解后端身份与可信数据

阅读 `backend/cmd/course-server/main.go`，再读 `backend/internal/tournament/`：

| 文件 | 要理解的问题 |
| --- | --- |
| `model.go` | 领域对象和只读 ChainReader 接口为什么不含签名/付款方法？ |
| `auth.go` | nonce、签名、JWT 各解决什么问题？为什么角色仍需从链上重新确认？ |
| `store.go` | 哪些数据可重建，哪些数据必须备份？为什么金额不使用 float？ |
| `chain.go` | ABI 如何编码只读调用、解码事件？为什么要检查 chain ID 和合约地址？ |
| `indexer.go` | 区块游标如何持久化？重复处理会不会重复记账？深度重组如何处理？ |
| `runner.go` | 如何运行、保存、恢复对战，如何生成完整证据？ |

练习：签名登录一次后重放同一 nonce；重启服务；重复同步同一批事件。分别确认拒绝、恢复和资金不重复累计。

数据库中 `financial_ledger` 来自确认后的事件。HTTP 请求成功、前端显示“已提交”、钱包弹出签名框都不等于资金已经完成转移。

## 第四步：理解 Agent 的能力与局限

阅读原有 `backend/internal/agent/agent.go`、`prompt.go`、`parser.go` 和课程 `runner.go`。

当前 Agent 根据游戏状态和性格构建输入，调用模型、解析动作、验证动作，再交给确定性引擎执行。模拟模式使用明确标识的规则策略，适合稳定演示和测试。

证据需要包括模型/模拟模式、Agent 定义、初始地图、每回合动作与结果、最终赢家。哈希可用于验证下载的原始 JSON 未被改变；它不证明后台没有在首次提交前伪造记录。独立审核仍然重要。

练习：下载证据，重新计算 Keccak-256；只改某一回合的动作，确认哈希发生变化。解释为什么只哈希最终血量不够。

后续 RAG 阶段再研究规则检索、工具调用、记忆、引用追溯及评估集。本轮不要把这些尚未实现的能力写进简历。

## 第五步：理解前端钱包体验

从 `frontend/src/lib/course.ts`、`useCourse.ts`、`useWalletTransaction.ts` 开始，再读首页和 `app/tournaments/[id]/page.tsx`。

跟踪一次赞助：输入十进制金额 → 校验小数位 → 转整数单位 → 检查钱包网络 → 估算 Gas → 授权 → 等待回执 → 注资 → 等待业务回执 → 刷新链上与索引状态。

练习：分别拒绝签名、切换钱包、切换网络、设置余额不足、在截止后报名，观察用户是否得到可理解的反馈。验证旧钱包的登录态不会沿用到新钱包。

## 第六步：形成自己的项目表达

下面是写作框架，不是未经验证的成绩：

> 我将原 AI 对战原型重构为赛事奖金托管系统。核心工作包括……。曾发现……问题，通过……修复，并用……测试证明。链上负责……，后端负责……。目前验证规模为……，实际限制为……。

优先准备的问题：

- 为什么使用四个交互合约，而不是一个大合约？
- 为什么 JWT 不能代替链上权限？
- 链事件到数据库如何保证幂等？
- 服务在比赛中途重启怎么办？
- 赞助资金一直不结算怎么办？
- 如何证明账本金额正确？如何处理精度？
- 如果审核员恶意、被撤权或失联，系统还能保证什么？
- 如何从单实例 SQLite 迁移到多实例？需要改变哪些一致性假设？

个人贡献按实际完成的代码、测试、文档和验证记录填写，区分黑客松旧工作与课程新增工作。
