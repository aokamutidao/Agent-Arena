# 课程版需求与验收标准

## 问题与用户

小型 AI 赛事有主办方、赞助方、参赛开发者和审核员。我们验证的问题是：奖池是否事先落实、领奖规则是否事先确定、结果和付款是否可追溯、赛事取消或停滞后如何退还赞助资金。

公开背景材料：FACEIT 的奖金流程要求提交团队分账方案，留出争议等待期，并采用批量付款。其说明以提交验证和分账信息后少于 45 天为处理目标，部分情形可能更长。
来源：https://support.faceit.com/hc/en-us/articles/9718204637596-How-do-I-claim-a-cash-prize-such-as-a-League-or-Cash-Cup-prize （本次查阅：2026-10-09）。

该资料只支持“赛事奖金结算存在实际复杂性”。它不能证明本项目已经解决真实组织的需求，也不能将身份核验、税务和争议等待全部归因于技术。正式报告需补充目标主办方/开发者的访谈或结构化用户测试。

## 本轮范围

- 一场赛事对应两名已报名的钱包及其不可变 Agent 定义。
- 主办方创建赛事；任何符合规则的钱包可以赞助。报名不收取费用。
- 奖池在开赛前预存；获胜者获得整场赞助奖池，无平台抽成。
- 报名有截止时间；结果有审核/异议窗口及最终结算期限。
- 主办方提交比赛结果；指定独立审核员确认或裁决；主办方不能单独划走奖金。
- 赛事取消或到期未完成时，赞助者按各自实际出资提取退款。
- 全部资金操作由用户钱包签名；后端不持有运营签名私钥。
- 复用原有游戏引擎及 Agent 决策代码。没有 LLM 配置时明确显示模拟运行，不伪称真实模型输出。

## 角色与利益相关者

| 角色 | 业务权限 | 约束 |
| --- | --- | --- |
| 平台管理员 | 分配/撤销组织者及审核员链上角色 | 不拥有任意提取奖池的能力 |
| 主办方 | 创建赛事、开赛、触发对战、提交结果、在规则允许时取消 | 只能管理自己的赛事 |
| 参赛者 | 创建 Agent、报名/退出、查看证据、提出异议、获胜后领奖 | 只能为自己的钱包报名和领奖 |
| 赞助方 | 注入奖池、查看资金与结果、符合条件时提出异议/退款 | 不能随意撤走已开赛奖池 |
| 审核员 | 查看证据、确认结果、处理争议 | 必须与该赛事的主办方、参赛者和赞助者身份分离 |

参赛和赞助是钱包的业务身份；admin/organizer/auditor 是实际执行权限控制的链上角色。JWT 只验证后端身份，资金权限最终由合约验证。前端隐藏按钮不是安全控制。

## 安全与非功能要求

1. 每场赛事资金独立记账；累计已付奖金/退款不超过实际到账金额。
2. 不能重复领奖、重复退款或利用事件重放重复记账。
3. 不接受不存在的赛事、零额出资、非法状态转换、过期报名。
4. 结算必须经历结果提交与完整异议窗口；到期无法完成时存在退出路径。
5. 登录挑战由服务端生成，绑定钱包、域名及 chain ID，单次消费且有到期时间。
6. 不通过 API 返回密钥；课程服务不接收任意外部 LLM URL 或用户模型 API Key。
7. 保存完整对局动作、配置、参赛者及结果快照，生成可重新计算的证据哈希。
8. 索引器从部署区块回填，保存游标和事件唯一键；数据库重启后可继续索引。
9. 链断连时显示未同步/不可用，不把本地猜测显示成已完成付款。
10. 用户取消签名、合约 revert、交易等待、RPC 错误有明确反馈。
11. 云部署使用持久磁盘、HTTPS、最小必要配置；备份恢复可操作。

## 评价计划（目标，尚非结果）

- 安全：越权、重放、双领、取消/退款、资金守恒及错误链用例通过。
- 可靠性：后端重启后赛事/事件可恢复，重复日志不重复累计金额。
- 性能：记录 API p50/p95、索引延迟、对战耗时和各交易 gasUsed。
- 可用性：邀请不同角色用户完成创建/赞助/报名/审核/领取任务，记录成功率、耗时和困惑点。
- 业务影响：在相同审核和争议规则下比较手工对账与系统对账的步骤/时间；不能拿测试网出块时间直接比较行业全流程处理周期。

## 范围外与实际限制

本轮不扩展 RAG、多链、NFT、淘汰赛或真实法币出入金。系统不自动判断比赛结果的真实性：审核员、后端及 LLM 仍有信任边界。真实采用还需评估身份核验、税务、隐私、资产规则、Gas 成本和钱包使用门槛。课程允许复用旧项目的规则及各成员贡献需如实说明。

## 为什么采用区块链，以及中心化方案何时更合适

这项设计的关键假设是：主办方、赞助者、开发者和审核员属于不同组织，并且不愿仅凭主办方的数据库截图相信奖池已经落实。

| 问题 | 常规中心化平台 | 本项目的链上机制 | 仍然存在的限制 |
| --- | --- | --- | --- |
| 资金是否真正预存 | 依赖平台账户、银行记录或可信第三方核验 | 可独立查询 ERC20 托管余额与每场账本 | 测试币无现实价值；真实代币另有发行与资产风险 |
| 规则是否临时修改 | 依赖平台治理、权限及审计制度 | 创建后固定参赛规模、审核员、截止和分配规则 | 管理员仍控制角色；链上代码缺陷可能不可逆 |
| 谁决定并执行付款 | 平台内部审批和支付账户 | 主办方提交、独立审核员确认、赢家自己领取 | 审核仍然需要可信的人和证据 |
| 平台失联如何退出 | 依赖服务恢复或外部追索 | 到期取消和按原出资退款无需服务器签名 | 用户仍需钱包、RPC、Gas，且规则不能照顾所有线下争议 |
| 如何核对历史 | 平台日志与导出报表 | 事件可独立重放，证据原文可比对链上 hash | 原文必须备份；链上透明不等于个人身份公开 |

如果所有参与者本就充分信任同一个组织，普通数据库、银行托管及审计日志可能更便宜、更易用。课程报告应解释本项目选择的是多方缺乏共同可信运营者的场景，而不是声称中心化技术无法付款。

## 实际采用与伦理讨论

- 报名提示词、对局记录和审核理由可公开查询；用户手册应提醒不要上传个人隐私或模型凭据。链上只存必要地址、金额和 hash，避免将可识别个人信息永久写链。
- 钱包地址不同不证明现实身份独立。主办方与审核员仍可能串通，当前机制缓解单一钱包的单方面操作，没有解决现实身份串谋。
- 超时退款保护赞助资金，但参赛者已经投入的时间可能无法补偿。主办方/审核员失联时，当前系统不能保证参赛者最终获得奖金。
- 单个有效异议会进入统一裁决状态；当前不支持多个平行案件、上诉、多签陪审团或审核员替换。
- 免费报名与赞助奖池降低了项目对观众押注的依赖；真实上线仍需由目标地区的业务和专业人员评估竞赛、税务、资产及数据处理要求。本课程原型没有提供法律或合规结论。
- 公网部署前需评估钱包门槛、Gas、RPC/LLM 服务费用、管理员密钥保管、独立审核员供给、数据库备份与可用性。
